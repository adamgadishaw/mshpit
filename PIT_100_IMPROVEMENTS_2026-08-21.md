# PIT: 100 verified improvements — 2026-08-21

This is the acceptance ledger for the 2026-08-21 improvement wave. It counts exactly 100 distinct changes, balanced as 25 items in each of four areas. Every entry states the concrete risk or usability problem, the implemented behavior, and the source/test evidence that defines acceptance. “Verified” means present in the current source tree and covered by the cited automated gate; it does not imply the broader certifications excluded under **Explicit non-claims / next gates**.

## Shared UI and interaction — 25 improvements

1. **Shared-button progress feedback.** **Why:** A silent control after activation can look unresponsive and invite repeat taps. **Implementation:** `Button` accepts `loading` and replaces its optional icon with an inline `ActivityIndicator` while retaining the title. **Evidence / acceptance:** `src/components/Button.jsx`; `src/domain/sharedUiAccessibility.test.mjs` requires both the loading prop path and spinner.

2. **Duplicate shared-button activation is blocked.** **Why:** A second press can duplicate a save, purchase-like action, or network mutation. **Implementation:** `blocked` is derived from `disabled || loading`, is passed to the native `disabled` prop, and removes the press handler while true. **Evidence / acceptance:** `src/components/Button.jsx`; the shared-UI regression test asserts the combined blocked state.

3. **Shared buttons expose name, purpose, and state.** **Why:** Assistive technology needs the same context sighted users receive from copy and progress styling. **Implementation:** Buttons accept an explicit accessibility label and hint, default the label to the title, and publish both `disabled` and `busy` state. **Evidence / acceptance:** `src/components/Button.jsx`; `sharedUiAccessibility.test.mjs` asserts the state contract.

4. **Compact buttons retain a platform-sized target.** **Why:** Visually compact actions previously fell below the 44-point iOS target recommendation. **Implementation:** The `small` variant has `minHeight: 44` while preserving compact typography and padding. **Evidence / acceptance:** `src/components/Button.jsx`; `sharedUiAccessibility.test.mjs` fails if the minimum height regresses.

5. **Screen titles are programmatic headings.** **Why:** A large font alone does not let a screen-reader user navigate by heading. **Implementation:** `ScreenHeader` assigns `accessibilityRole="header"` to its title. **Evidence / acceptance:** `src/components/ScreenHeader.jsx`; the shared-header test asserts the header role.

6. **Back controls can describe their destination.** **Why:** Repeating “Go back” is ambiguous in nested flows. **Implementation:** `ScreenHeader` accepts `backLabel` and `backHint`, defaults safely to “Go back,” and forwards both to the back button. **Evidence / acceptance:** `src/components/ScreenHeader.jsx`; `sharedUiAccessibility.test.mjs` asserts the default and hint path.

7. **Sheet lead controls are 44 by 44 points.** **Why:** Close/back icons were easy to miss on touch screens. **Implementation:** `SheetHeader` fixes the lead button at `44 × 44`, with hit slop in addition to—not instead of—the visible target. **Evidence / acceptance:** `src/components/SheetHeader.jsx`; the shared-button regression test asserts both dimensions.

8. **Sheet actions show in-control progress.** **Why:** A modal save that does not acknowledge work encourages repeated activation. **Implementation:** An action with `loading: true` renders an `ActivityIndicator` next to its label. **Evidence / acceptance:** `src/components/SheetHeader.jsx`; `sharedUiAccessibility.test.mjs` requires the loading branch.

9. **Busy sheet actions are non-repeatable and announced.** **Why:** Visual progress without an actual lock still permits duplicate mutations. **Implementation:** `actionBlocked` combines disabled/loading, disables the `Pressable`, suppresses its handler, publishes busy/disabled state, and preserves the action hint. **Evidence / acceptance:** `src/components/SheetHeader.jsx`; the shared-UI test asserts the combined state expression.

10. **Sheet title and lead-control semantics are explicit.** **Why:** Modal headers need both a discoverable heading and contextual navigation. **Implementation:** The title is a header; the lead control has button role, Back/Close label, optional hint, and disabled state. **Evidence / acceptance:** `src/components/SheetHeader.jsx`; the shared-header regression test requires title and lead hint semantics.

11. **A render crash is announced as an urgent error.** **Why:** Replacing the app with a recovery screen can otherwise be silent to screen-reader users. **Implementation:** `ErrorBoundary` renders an assertive alert container and a programmatic heading around the recovery explanation. **Evidence / acceptance:** `src/components/ErrorBoundary.jsx`; `sharedUiAccessibility.test.mjs` asserts live-region and heading markers.

12. **Local-data reset requires deliberate confirmation.** **Why:** A single accidental press would sign the user out and erase hydrated local state. **Implementation:** The first press arms reset and changes the control to “Tap again to confirm”; only a second press performs removal and reload. **Evidence / acceptance:** `src/components/ErrorBoundary.jsx`; the crash-recovery test asserts the armed state and confirmation copy.

13. **Reset confirmation expires safely.** **Why:** A destructive control must not remain armed after the user’s attention moves elsewhere. **Implementation:** The armed state clears after eight seconds; the timer is cleared on confirmed reset and component unmount. **Evidence / acceptance:** `src/components/ErrorBoundary.jsx`; the regression test asserts the 8,000 ms timeout and unmount cleanup.

14. **Crash-recovery actions work beyond pointer input.** **Why:** Recovery is most important when the app is degraded, so keyboard focus and control identity cannot be implicit. **Implementation:** Retry, reload, and reset are labelled buttons with visible focus-ring and pressed feedback. **Evidence / acceptance:** `src/components/ErrorBoundary.jsx`; `sharedUiAccessibility.test.mjs` requires button, focus, and pressed-state paths.

15. **Feedback urgency matches severity.** **Why:** Announcing every informational toast assertively interrupts current screen-reader speech, while errors should interrupt. **Implementation:** Info messages use a polite live region; warning, error, and fatal messages use assertive announcement. **Evidence / acceptance:** `src/components/FeedbackHost.jsx`; the feedback regression test asserts the severity mapping.

24. **Ratings support complete keyboard adjustment.** **Why:** Pointer-coordinate rating controls exclude keyboard users. **Implementation:** `TapStars` maps arrows to ±0.5, Home to 0, and End to 5 while preventing the browser’s conflicting default behavior. **Evidence / acceptance:** `src/components/TapStars.jsx`; the rating-control test asserts Home, End, and bounded adjustment code.

## Accessibility and forms — 25 improvements

26. **Authentication has one real pending lock.** **Why:** Login, signup, and reset-link requests could otherwise overlap or be submitted twice. **Implementation:** `busyAction` identifies the active auth operation; submit handlers return while busy, relevant fields/actions become disabled, and controls expose busy state. **Evidence / acceptance:** `src/screens/AuthScreen.jsx`; `src/domain/screenAccessibilityWave.test.mjs` asserts pending state and disabled submit wiring.

27. **Authentication reports server-confirmed outcomes only.** **Why:** Optimistic success can tell a user an account or reset email exists before persistence/network completion. **Implementation:** Login/signup/forgot-password handlers await their store mutation, branch on its returned result, and clear the pending lock in `finally`. **Evidence / acceptance:** `src/screens/AuthScreen.jsx`; source acceptance is the awaited `login`, `signup`, and `forgotPassword` calls guarded by `busyAction`.

28. **Auth fields describe autofill and keyboard intent.** **Why:** Generic text inputs create worse password-manager, mobile keyboard, and form-advance behavior. **Implementation:** Name/email/current-password/new-password fields provide appropriate `autoComplete`, `textContentType`, capitalization, keyboard type, and return-key metadata. **Evidence / acceptance:** `src/screens/AuthScreen.jsx`; the auth regression test requires the three autofill tokens.

29. **Terms and analytics choices are full-row checkboxes.** **Why:** Tiny boxes and visual-only checks are hard to operate and understand. **Implementation:** The full consent rows are press targets with checkbox role, checked/disabled state, descriptive labels, and mutation lockout; optional analytics starts off. **Evidence / acceptance:** `src/screens/AuthScreen.jsx`; `screenAccessibilityWave.test.mjs` plus source assertions cover checked and disabled state.

30. **Auth status messages use the correct announcement channel.** **Why:** Validation failures require prompt attention, while a reset-email confirmation should not interrupt. **Implementation:** Errors are assertive alerts; reset confirmation is a polite status under a heading and uses enumeration-resistant copy. **Evidence / acceptance:** `src/screens/AuthScreen.jsx`; the auth regression test asserts assertive errors, and source contains the polite confirmation region.

31. **Secondary auth actions remain usable while respecting locks.** **Why:** Forgot-password, mode switching, Terms, and Privacy links were smaller or semantically generic. **Implementation:** These controls have explicit button/link roles, disabled state during mutation, and a 44-point minimum-height shared secondary style. **Evidence / acceptance:** `src/screens/AuthScreen.jsx`; source-level acceptance covers roles, disabled state, and `switchButton`/`inlineLink` target styles.

32. **Password reset prevents concurrent saves.** **Why:** Repeated reset submissions can race token consumption and produce contradictory results. **Implementation:** `submit` returns if `busy`, all fields and Cancel lock during save, and the submit control publishes disabled/busy state. **Evidence / acceptance:** `src/screens/ResetPasswordScreen.jsx`; `screenAccessibilityWave.test.mjs` asserts early return and busy semantics.

33. **Password-reset fields expose purpose and errors.** **Why:** Two masked fields are indistinguishable without labels and autofill metadata. **Implementation:** Both fields have explicit labels/disabled state; the new value has a strength hint and new-password autofill; mismatch/server errors use an assertive alert. **Evidence / acceptance:** `src/screens/ResetPasswordScreen.jsx`; the reset regression test requires new-password autocomplete and live error wiring.

34. **Artist onboarding commits theme only after profile save.** **Why:** Applying the theme before the artist/genre mutation succeeds leaves the UI and account record out of sync. **Implementation:** `themeChoice` is staged locally; `updateProfile` is awaited; `chooseTheme` runs only after a successful result. **Evidence / acceptance:** `src/screens/PickArtistsScreen.jsx`; the onboarding regression test asserts local selection wiring, and source order establishes save-before-theme.

35. **Artist tiles expose checked selection without duplicate art.** **Why:** Selected styling is not a programmatic state, and decorative artwork can repeat the artist name. **Implementation:** Tiles use checkbox role with checked/disabled state; decorative image content is excluded from accessibility. **Evidence / acceptance:** `src/screens/PickArtistsScreen.jsx`; `screenAccessibilityWave.test.mjs` asserts checkbox state and the scoped JSX parses.

36. **Artist choices lock and surface a failed save.** **Why:** Editing while persistence is in flight can submit a different set than the one shown; swallowed failure loses trust. **Implementation:** Search, tiles, theme choices, and submit honor `saving`; rejected/unsuccessful results leave the screen open and render an assertive error. **Evidence / acceptance:** `src/screens/PickArtistsScreen.jsx`; the scoped screen regression covers disabled artist state and parse integrity.

37. **Artist search can be cleared and announces no matches.** **Why:** A small unlabeled clear glyph and silent empty grid create a dead end. **Implementation:** Clear is a 44-point labelled button disabled during save; zero results render a polite status naming the query. **Evidence / acceptance:** `src/screens/PickArtistsScreen.jsx`; `screenAccessibilityWave.test.mjs` asserts the clear label and source includes the live empty status.

## Social, music, and privacy — 25 improvements

51. **Listening History has a dedicated lazy route.** **Why:** Recent plays were data without a user-accessible destination. **Implementation:** `App.js` lazy-loads `ListeningHistoryScreen`, registers overlay analytics/navigation, and adds a You-screen entry. **Evidence / acceptance:** `App.js`, `src/screens/YouScreen.jsx`, and `src/screens/ListeningHistoryScreen.jsx`; a successful export proves the lazy module resolves.

52. **History replay preserves recording/provider identity.** **Why:** Replaying by display label alone can select the wrong recording or lose an existing video/preview URL. **Implementation:** `listeningHistoryReplayTrack` retains the stored catalog/source/provider fields, normalizes the required title/artist and media URLs, and keeps `playId` separate from track ID. **Evidence / acceptance:** `src/domain/listeningHistoryView.mjs`; its test asserts catalog ID, event ID, provider/video data, and invalid-row rejection.

53. **Account changes hide the previous account’s history immediately.** **Why:** Effect-based clearing can flash account A’s private listening data after switching to B. **Implementation:** Store exports history only when `playHistoryAccountId` equals the render-time active account; an unscoped view receives no rows/cursor/error. **Evidence / acceptance:** `src/store.js`, `src/domain/accountPrivateProjection.mjs`; its A-to-B regression asserts zero leaked rows before effects run.

54. **History presents truthful lifecycle states.** **Why:** Loading, refresh failure, empty history, and pagination failure require different actions and copy. **Implementation:** A pure view-state reducer distinguishes signed-out, loading, error, empty, ready, refreshing, refresh-error, loading-more, and page-error. **Evidence / acceptance:** `src/domain/listeningHistoryView.mjs`; the state-table test asserts every transition explicitly.

55. **History offers cursor-aware recovery and pagination.** **Why:** A failed later page should not erase already loaded plays or be confused with a first-load error. **Implementation:** The screen has refresh, retry, load-older, page-specific retry, loading footer, and end-of-window copy; the store tracks cursor and `errorMode`. **Evidence / acceptance:** `src/screens/ListeningHistoryScreen.jsx`, `src/store.js`; view-state tests assert refresh/page error separation.

56. **Repeated plays have distinct, stable list keys.** **Why:** Keying by song identity collapses two separate listening events and can recycle the wrong row. **Implementation:** Rows prefer durable `playId`; the fallback combines event fields and index so repeated copies remain distinct. **Evidence / acceptance:** `src/domain/listeningHistoryView.mjs`; its regression asserts different keys for two identical song events and exact `play:p1` identity.

57. **Recommendations consume only current-account history.** **Why:** Account B’s recommendations and favorite genre must not be influenced by account A’s cached plays. **Implementation:** Favorite-genre derivation, recommendation candidates, autoplay, and exposed context consume `scopedPlayHistory`, never raw state. **Evidence / acceptance:** `src/store.js`; `accountPrivateProjection.test.mjs` source-checks each consumer and asserts B falls back to B’s genre.

58. **Private playlists are render-time account scoped.** **Why:** Clearing playlists in an effect still permits one render of another account’s private names/tracks and lets late mutations cross ownership. **Implementation:** Playlist state stores `{accountId, rows}`; reads/status are projected by the active account, and create/update/delete writes target the current account bucket. **Evidence / acceptance:** `src/store.js`; `accountPrivateProjection.test.mjs` asserts A’s private playlist is absent for B.

59. **Artist requests require a canonical server ID.** **Why:** A locally invented success row can disagree with moderation state or duplicate a later response. **Implementation:** The store awaits POST, accepts only the server-returned trimmed 2–120 character safe identifier, merges only that confirmed object, and then returns success. **Evidence / acceptance:** `src/domain/artistRequestMutation.mjs`, `src/store.js`; tests reject missing/whitespace-padded/malformed IDs and assert await-before-insert.

60. **A failed artist request preserves user work and creates no ghost row.** **Why:** Clearing the form or inserting pending state after an outage falsely signals submission. **Implementation:** Failure returns safe inline copy, leaves screen inputs intact, and `mergeConfirmedArtistRequest` is a no-op without a confirmed row. **Evidence / acceptance:** `artistRequestMutation.test.mjs` asserts no merge on null and sanitizes internal error text; `RequestArtistScreen.jsx` clears only after success.

61. **Authoritative profile unavailability quarantines cached private content.** **Why:** Retaining cache after 403/404/410 can reveal a blocked, removed, or no-longer-public profile and media. **Implementation:** Those statuses map to `missing` with `evict: true`; profile user and authored post cache are removed. **Evidence / acceptance:** `src/domain/profileReadState.mjs`, `src/store.js`; tests iterate all three statuses and assert target user/posts disappear.

62. **Transient profile failure labels retained cache as stale.** **Why:** Cached data may remain useful during an outage but must not be represented as current. **Implementation:** A transient error with cache returns `stale`, retains data, and renders an explicit refresh-failed message. **Evidence / acceptance:** `src/domain/profileReadState.mjs`, `src/screens/ProfileScreen.jsx`; tests assert the exact stale outcome and visible stale copy.

75. **Discover tracks can be added without first playing them.** **Why:** Chart, genre, and friend-listening discovery previously offered playback but no direct collection workflow. **Implementation:** Exact track descriptors flow to labelled, 44-point add-to-playlist actions in all three surfaces and through `DiscoverScreen`/`App.js`. **Evidence / acceptance:** `src/components/discover/DiscoverChart.jsx`, `DiscoverGenres.jsx`, `DiscoverCommunity.jsx`, `src/screens/DiscoverScreen.jsx`, and `App.js`.

## Server reliability, privacy, and operations — 25 improvements

76. **API responses are private by default.** **Why:** Authenticated JSON cached by browsers or intermediaries can leak across sessions; error/preflight paths must not be exceptions. **Implementation:** the HTTP bridge initializes success, error, and OPTIONS headers with `Cache-Control: no-store`; only an allow-listed bounded setter can override it for a deliberate public route. **Evidence / acceptance:** `server/responseHeaders.js`, `server/index.js`; `server/responseHeaders.test.mjs` asserts default and safe override.

77. **Public health reveals only liveness and public capabilities.** **Why:** Commit IDs, quotas, storage posture, and mail configuration help an attacker inventory deployment weaknesses. **Implementation:** `/api/health` returns only `ok`, timestamp, and photo/video publishing capabilities after readiness checks. **Evidence / acceptance:** `server/api.js`; `server/api.integrity.test.mjs` asserts the exact three-key projection and absence of services/commit.

78. **Detailed health requires an active staff account.** **Why:** Operators still need diagnostics, but they are not public metadata. **Implementation:** `/api/admin/health` is guarded by `requireModerator` and contains uptime, storage, provider quota, job, mail, and media diagnostics. **Evidence / acceptance:** `server/api.js`; the health test verifies moderator access and 403 for a fan.

79. **Malformed encoded route identities return controlled 400 errors.** **Why:** `decodeURIComponent` throws on bad percent encoding, which previously escaped as a 500. **Implementation:** `decodedPathParam` catches decode failures and raises `VALIDATION_FAILED`; all artist, fan-club, lounge, attendee, venue, and artist-UGC encoded paths use it. **Evidence / acceptance:** `server/api.js`; `api.integrity.test.mjs` executes malformed input against 14 route variants and expects 400.

80. **Overlong decoded route identities are rejected, not truncated.** **Why:** Truncation can make two distinct URLs alias the same authorization or pagination resource. **Implementation:** The helper bounds raw encoded length, measures decoded Unicode code points, rejects values above each route maximum, and only then cleans text. **Evidence / acceptance:** `server/api.js`; the encoded-route test submits an 81-character fan-club artist and requires `VALIDATION_FAILED`.

81. **Feed, clip, and post projections exclude inactive authors and signals.** **Why:** Banned or currently suspended accounts must not remain visible through alternate read paths or inflate preview engagement. **Implementation:** Shared active-account SQL gates post rows plus like/comment preview subqueries across direct post, feed, clips, and profile posts. **Evidence / acceptance:** `server/accountVisibility.js`, `server/api.js`; the public-UGC matrix tests active, live-suspended, expired-suspension, and banned cases.

82. **Member-derived public surfaces share one active-account predicate.** **Why:** Fixing only people search leaves profile, follow lists, playlists, badges, or rewards as identity side channels. **Implementation:** `accountIsPublic`/`activeAccountSql` gates public lookup, profile stats/lists, non-owner playlists, rewards/badges, and related projections while preserving self access where intended. **Evidence / acceptance:** `server/accountVisibility.js`, `server/api.js`; the visibility and block-matrix tests cover cross-surface absence.

83. **Post interactions reject an inactive author target.** **Why:** Hidden content must not remain mutable through a known post ID. **Implementation:** Like and comment write routes load the target and reject missing, removed, or non-public authors before mutation. **Evidence / acceptance:** `server/api.js`; `api.integrity.test.mjs` covers inaccessible target writes in the block matrix and public visibility policy.

84. **Comment reads hide inactive authors without breaking reply structure.** **Why:** Removing a parent outright can orphan visible replies; exposing its text violates account visibility. **Implementation:** Active authors are selected; deleted/hidden parents needed by descendants are represented as empty tombstones, while removable leaves are omitted and returned as removed IDs. **Evidence / acceptance:** `server/api.js`; comment-integrity and public-UGC tests assert exclusion, tombstone text removal, and preserved `parentId`.

85. **Author post deletion scrubs authored content and bindings.** **Why:** Marking `removed=1` alone retains review text, ratings, media, setlists, songs, playlists, entity bindings, and idempotency material. **Implementation:** The delete mutation atomically blanks/nulls all authored fields, preserves a minimal foreign-key tombstone, and remains owner-only/idempotent. **Evidence / acceptance:** `server/api.js`; `server/post.edit.test.mjs` asserts every scrubbed column and one audit record across repeated delete.

86. **Fan-club counts and messages filter before limiting.** **Why:** Filtering after pagination leaks restricted membership counts and can return short/empty pages despite later visible rows. **Implementation:** Directory aggregates, metadata counts, member counts, and message SQL join users and apply active-account plus viewer-block policy before ordering/limit. **Evidence / acceptance:** `server/api.js`; fan-directory, block-matrix, and public-UGC tests verify visible counts/messages.

87. **Lounge counts and messages filter before limiting.** **Why:** Suspended/banned/blocked participants must not appear in after-show counts or consume page slots. **Implementation:** Attendee and lounge-message queries apply active-account and bilateral block predicates inside SQL before count/order/pagination. **Evidence / acceptance:** `server/api.js`; block-matrix and public-UGC tests assert hidden attendee/message rows and counts.

88. **Venue reviews and artist UGC obey account visibility.** **Why:** These public surfaces could otherwise republish restricted author text or media after the main feed hides it. **Implementation:** Venue-review and artist-post/profile queries join active authors; an inactive artist-profile owner produces null profile/posts, with viewer blocks applied before paging. **Evidence / acceptance:** `server/api.js`; the public-UGC matrix asserts venue and artist surfaces across active and suspended states.

89. **Public/member tour reads hide rows from inactive owners.** **Why:** A suspended artist account’s self-published dates should not remain public, but provider inventory and staff investigation access should remain available. **Implementation:** Non-admin reads left-join owner and require active owner/release policy only when `owner_id` exists; ownerless provider rows remain visible, while the explicit admin branch retains oversight access. **Evidence / acceptance:** `server/api.js`; public-UGC tests hide an authored tour row, and provider-isolated cleanup tests preserve owner rows.

90. **SEO output follows the same inactive-account policy.** **Why:** Hidden API content can still leak through Open Graph tags, entity routing, aggregates, static share HTML, or sitemaps. **Implementation:** SEO profile/show/venue lookup, artist/venue aggregates, routing, head injection, and sitemap queries all require active authors. **Evidence / acceptance:** `server/seo.js`; `server/seo.test.mjs` asserts fallback metadata and exclusion of restricted URLs/names/counts.

91. **Ratings and recommendation engagement ignore inactive users.** **Why:** Hidden accounts should neither affect displayed rating aggregates nor rank other content through likes/comments. **Implementation:** Rating counts/averages and recommendation candidate/signal subqueries join users and apply the shared active-account SQL. **Evidence / acceptance:** `server/api.js`, `server/recommendationService.js`; public-UGC tests assert rating count drops to zero when the author is suspended.

92. **Inbox summaries avoid per-thread message hydration.** **Why:** Loading up to 500 messages separately for every conversation creates an N+1 query and payload multiplier. **Implementation:** Summary mode uses one `ROW_NUMBER() OVER (PARTITION BY other_id …)` query to return the latest message per peer; full thread hydration remains available only when requested. **Evidence / acceptance:** `server/api.js`; the capped-social test asserts summary returns one latest message while full mode preserves its bounded history window.

93. **Campaign draining is single-flight within this process.** **Why:** Concurrent drains can both consume the same provider quota slot or race campaign state. **Implementation:** Active drains deduplicate by campaign ID and a fulfilled promise tail serializes all local campaigns around the daily-slot check/send section. **Evidence / acceptance:** `server/emailQueue.js`; `server/emailCampaign.test.mjs` asserts shared promise/single send and two campaigns contending for the final local slot.

94. **Email delivery uses atomic expiring token-owned claims.** **Why:** Resetting every “sending” row on each drain lets two workers deliver one address twice; a late worker must not settle a reclaimed row. **Implementation:** One SQL `UPDATE … RETURNING` claims a pending row with timestamp/UUID, only expired leases are reclaimed, and settlement requires the same token. **Evidence / acceptance:** `server/db.js`, `server/emailQueue.js`; campaign tests assert claim ownership, expiry, and stale-settlement rejection.

95. **Provider/config outages preserve a retryable recipient.** **Why:** Treating deployment failure as a recipient skip permanently loses delivery, while continuing can burn the whole queue. **Implementation:** Unknown delivery failures restore the token-owned row to pending, stop after that address, and reuse a row-derived idempotency key on retry. **Evidence / acceptance:** `server/emailQueue.js`; outage and resume tests assert one-address pause, same row, and exactly one eventual delivery.

96. **Email retry exhaustion ends as failed, never sent.** **Why:** A poison configuration must be bounded without falsely marking the campaign successful. **Implementation:** Claim time increments attempts; the third provider failure settles the row `failed`; campaign terminal state derives from failed count. **Evidence / acceptance:** `server/emailQueue.js`; the all-outage test runs bounded attempts and asserts row/campaign are failed rather than sent.

97. **Campaign completion requires no open queue rows.** **Why:** Finalizing while a row is pending or leased can strand recipients and misreport delivery. **Implementation:** Completion checks `pending` plus `sending`; only zero open rows permits terminal status, selected as failed when any terminal failure exists and sent otherwise. **Evidence / acceptance:** `server/db.js`, `server/emailQueue.js`; concurrency/outage campaign tests assert durable final state.

98. **A test email approves one exact content revision.** **Why:** Editing subject/body after a test—or a delayed test response—must not authorize unreviewed copy. **Implementation:** Content edits atomically increment `content_revision` and clear approval; test settlement records only its captured revision; send verifies `tested_revision === content_revision` inside the start transaction. **Evidence / acceptance:** `server/db.js`, `server/emailQueue.js`; tests cover edit invalidation, delayed stale test, and PATCH/send serialization.

99. **Concurrent campaign Pause remains authoritative.** **Why:** A drain that finishes after Pause must not claim another recipient or overwrite the operator’s state. **Implementation:** Claim SQL requires campaign `sending`; settlement may finish the already in-flight row, then durable status stops the loop; finalization updates only a sending campaign. **Evidence / acceptance:** `server/emailCampaign.test.mjs` pauses during delivery and asserts no second claim and final status remains paused.

100. **Tour cleanup is provider-isolated and success-gated.** **Why:** A partial Ticketmaster/Bandsintown outage must not erase valid cache, another provider’s rows, or artist-authored dates. **Implementation:** Refresh tracks success/failure per provider, reconciles stale ownerless rows only for a provider whose every attempted call succeeded, and records freshness only after a fully successful run. **Evidence / acceptance:** `server/tourdates.js`; `server/cacheWarmer.test.mjs` asserts provider isolation, owner preservation, empty-success handling, and retry-due partial failure.

## Explicit non-claims / next gates

- Accessibility coverage here is source, logic, parser, test, and export verification. It is **not** physical-device VoiceOver/TalkBack certification, switch-control certification, or a full WCAG conformance audit. Those require representative iOS/Android hardware, screen readers, text scaling, orientation, and keyboard/switch runs.
- The 44-point statements apply only to the named controls and styles evidenced above. WCAG 2.2’s target-size criterion has exceptions and a different minimum; this ledger does not generalize a component assertion to every control in PIT.
- Abort/version ownership prevents stale client commits; it does not make third-party catalogue, image, email, or video providers available. Live provider soak and degraded-network testing remain release gates.
- `Cache-Control: no-store` is the API default. Deliberately public endpoints may override it through the bounded allow-list; this is not a claim that all responses are uncacheable.
- “Inactive” means banned or suspended until a future timestamp under `server/accountVisibility.js`. An expired suspension becomes public again without rewriting content; this is visibility policy, not deletion.
- Email daily-slot serialization is process-local for the current single-process deployment. Multi-instance scaling requires a durable distributed quota reservation/lock.
- Token-owned database leases prevent stale workers from settling a reclaimed row. End-to-end duplicate suppression across provider ambiguity also depends on the provider honoring the stable idempotency key; this is not a mathematical exactly-once delivery claim.
- Inbox item 92 optimizes summary mode. Full conversation mode intentionally returns its bounded history window and is not claimed to be a constant-size payload.
- Existing synchronous password hashing, process-local request limiting, and synchronous bounded account export were audited but are not claimed as fixed in this wave.
- Tour reconciliation is limited to the named Ticketmaster/Bandsintown provider rows and never asserts that external inventories are complete.
- This ledger does not claim a production deployment or App Store readiness. Commit/push identity, remote CI status, hosted smoke testing, native build credentials, privacy nutrition labels, screenshots, and store review metadata require separate evidence.
