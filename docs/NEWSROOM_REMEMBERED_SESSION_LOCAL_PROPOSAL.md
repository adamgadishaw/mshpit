# Remembered Newsroom browser — local candidate

The owner approved the Newsroom-only policy and release on 2026-10-21, conditional on updated tests and compatible deployment. This does not grant full administration through remembered access or issue any user's credential automatically. Production activation and per-browser opt-in are separate steps in the release sequence below.

## Approved duration and entry

The absolute maximum is **30 days**, with a **7-day inactivity window** refreshed on each successful scoped session confirmation. Renewal never moves the original creation time or absolute deadline. `NEWSROOM_BROWSER_SESSIONS_ENABLED` defaults to false. Disabled code cannot issue or authorize a scoped session, and starting the compatible server with the flag disabled clears scoped rows. Activate only after every serving instance is compatible and healthy.

A browser user first signs in normally, then opens `/newsroom-remembered.html` from the full Newsroom link or a bookmark. Explicit enable requires both a valid normal admin/editor session and fresh password verification. A remembered Newsroom cookie alone cannot enable another session or recover lost credentials. Password input is sent once over the existing same-origin authentication boundary and cleared; it is never persisted. Full staff authority remains subject to the existing 12-hour admin/moderator cap. The two cookie sessions can coexist while full authority is still valid; the remembered cookie never extends it or grants it back after expiry.

The dedicated page confirms only a Newsroom identity and never installs an admin identity into the main app. Its article form and photo retry state live only in memory. Error parsing follows the real server `{error: string, code: string}` envelope. On expiry, revocation, policy disablement or identity mismatch, the editor, files and old identity are cleared from the DOM. Unsaved text fields may remain only in this tab, keyed to the original confirmed account; a fresh successful check of that same scoped identity plus an explicit Restore action is required to display them again. Another account cannot restore them, and an identity change during restore is rechecked before any field is populated. No passwords, session tokens or photo bytes enter this held-text buffer. Explicit Forget clears all held text, files and password inputs immediately, including on identity conflict or transport failure; the request retains the intended account header and reports whether server revocation was confirmed. closing/reloading the tab loses it. The sign-in link opens another tab so returning to the original tab is possible without hidden storage or credential recovery. Photos must be reselected after restoring unsaved text. Saved drafts live on the server. After reload, preview an owned saved draft and select **Edit a copy** to restore its fields, sources and photo provenance. Saving the copy preserves the original and reuses its owned verified photo unless a new file is selected. Stable in-memory save keys and file identity support safe retries after transfer or response failures; nothing is recovered from hidden browser storage. No credential, password, token, fingerprint, automatic password login or credential recovery is placed in localStorage, IndexedDB or a service worker.

## Exact authorization scope

The server recognizes only these Newsroom routes for the separate cookie. Unknown routes/methods and every legacy API route are outside this authorization context by default.

| Method and route | Allowed work and restrictions |
| --- | --- |
| `POST /api/me/newsroom-session` | Enable with normal full staff session plus fresh password. **Not** callable using remembered authority. No duration/scope/role/body override. |
| `GET /api/newsroom-session/status` | Confirm current verified actor, scope and expiry; may renew idle window. Returns no admin role, member settings, email or staff overview. |
| `POST /api/newsroom-session/logout` | Revoke this remembered browser row and expire its cookie. |
| `POST /api/newsroom-session/logout-all` | Revoke all remembered Newsroom browser rows for this actor only. Does not extend or erase other normal full sessions. |
| `GET /api/newsroom-session/drafts` | At most 20 of this actor's self-written drafts/publications created through this scope. |
| `POST /api/newsroom-session/drafts` | Save self-written headline, summary, body, category, source citations, bound photo provenance and stable retry key. No generated draft call. |
| `GET /api/newsroom-session/drafts/:id` | Preview the exact own scoped article, sources and verified image derivative. |
| `POST /api/newsroom-session/drafts/:id/publish` | Publish only that own self-written scoped draft, with mandatory matching preview revision and existing article/source/photo/publisher checks. |
| `POST /api/newsroom-session/drafts/:id/discard` | Discard own scoped unpublished draft. No published-story deletion or editing. |
| `POST /api/newsroom-session/media` | Request a bound article-photo ticket: JPEG/PNG/WebP only, maximum 10 MiB, forced post purpose, scoped client ID, six requests/hour plus a durable 12-attempt rolling-day limit. Existing media quotas and circuit breakers remain. |
| `GET /api/newsroom-session/media/:id` | Read only an actor-owned asset admitted through this scope. |
| `POST /api/newsroom-session/media/:id/finalize` | Finalize only that bound photo using existing server derivative verification; no client variants, delivery-mode override, video or arbitrary object key/URL. |

Sources are validated citation fields saved with the article; there is **no arbitrary source-fetch endpoint**. Preview is a read of the saved own draft, not a general staff overview or arbitrary URL renderer. Existing article expiry remains (currently one day); a thirty-day login does not keep an old draft publishable forever. Reworking article fields saves another draft rather than mutating a published article.

Generated drafts, source discovery/fetching, generated-news limits/configuration, shared staff drafts, unrelated moderation, member data/export, account settings/password/permissions, API credential grants, live coverage, arbitrary uploads, avatar/banner assets, media variants, video, and published category/share-artwork changes are not in the scope. Public anonymous pages remain public; the cookie grants no identity there.

## Server boundaries and revocation

- Scoped token hashes live only in the additive `newsroom_browser_sessions` table, outside legacy `sessions`. Even an old full-session lookup cannot resolve them. `getSession` defaults to full scope and refuses a Newsroom token even if it is copied into the normal cookie name. Request authorization separately checks an exact route allowlist and rechecks live authority after body buffering and in existing async/mutation guards.
- The Newsroom cookie is separately named `__Host-pit_newsroom` in production: Secure, HttpOnly, SameSite=Lax, Path=/, no Domain. The database stores only the SHA-256 hash of a random 256-bit token. The raw token is not a second bearer API grant or returned JSON credential.
- Actor role must remain the role at issuance and be admin/editor, verified, active, unsuspended and unbanned. A database trigger revokes scoped rows on any role or password-hash change, suspension change, dormancy, ban or loss of verification. Role loss followed by restoration cannot resurrect a credential.
- Normal website logout revokes the presented Newsroom cookie too, even if its full staff session already expired. Password change/reset and ordinary account-wide revocation delete scoped rows as well. Explicit scoped logout-all provides revocation from the dedicated page. Owner adoption/transfer also revokes all existing admin cookies in both stores within the existing transaction, including unchanged peer-admin accounts.
- New normal sign-in/account switching/recovery retires any previous remembered Newsroom cookie in that browser. Remembering must be explicitly enabled again after fresh authentication. Existing CSRF/origin, expected-account, account restriction and role checks remain in force.
- Draft reads/publish require actor ownership, `origin=self_written`, `created_actor_type=newsroom_browser`, and no API grant ID. Photo reads/writes require their own scope admission record and owner. Saving/publishing retain attribution and recheck authority inside the existing transaction before commit. Paid/generated work is never invoked.

## Threat model and tradeoffs

This reduces daily password entry for the self-written Newsroom workflow while the browser retains a valid authorized cookie. It does not automatically sign anyone into the founder account. Cleared cookies, disposed private contexts, expired windows and revoked database rows require a new sign-in/explicit enable. There is no recovery or resurrection from another browser store.

A stolen scoped cookie can publish or discard the owner's scoped self-written articles and use the bounded photo allowance until revoked or expired. That is still consequential brand/publication access. An attacker may renew its idle window, but cannot exceed thirty days from issuance, expand its scope, change permissions, read member data or call the generated news controls. HttpOnly and TLS do not eliminate same-origin script compromise. Held unsaved text is plaintext only in the original tab memory: the same-account restore check protects the UI, not against developer tools, same-origin script compromise or someone controlling the browser process. Forget or closing the tab discards that buffer; it is never written to web storage. Clearing local cookies removes the browser's proof; it does not revoke a stolen copy elsewhere, so use logout/revocation for that.

Previously issued storage PUT URLs can remain usable until their existing short signed-ticket expiry. Revocation prevents subsequent session-authorized finalization/publication; it cannot undo bytes already transferred or articles already published. This candidate does not claim exactly-once external upload or immediate cancellation of a previously issued storage signature.

Review follows [OWASP authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) on least privilege, default denial, per-request checks and ownership, and the previously reviewed [OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) and [MDN cookie guidance](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie). No particular assurance/compliance certification is claimed.

## Diagnosis and browser limits

The existing `server/auth.js` uses `sessionTtlForRole` to set admin/moderator expiry to 12 hours in `createSession`, and `getSession` re-applies that cap from live role on every lookup. The normal `/api/me` request does not renew it. Production cookies already carry an explicit expiry, so normal browser closure alone is not proof of a server-session loss. The cap is an intentional code security boundary; its original rationale beyond limiting elevated-session lifetime is an inference, not documented incident evidence. Historical cloud browser profile resets or cookie loss were not independently observable here. This task made no live authenticated browser requests and cannot establish which mechanism caused each past sign-out. The proposal helps only while this same browser retains an authorized scoped cookie. It cannot survive cleared cookies, private-context disposal or lost cloud browser profiles.

## Rollout and rollback boundary

An old server does not understand the scoped cookie or its logout behavior. Separate storage prevents elevation to full staff access, but old-version logout cannot invalidate that scoped row. Keep the gate disabled until every serving instance runs compatible code. Before any rollback, disable the gate and restart the current version to purge scoped rows; verify the scoped store is empty before serving an older version. Never restore scoped session rows from a backup when re-enabling. A mixed-version or rollback operation that skips this invalidation is not approved by this proposal. No rollout, rollback or database operation was performed here.

## Local browser acceptance status

The real-envelope regression tests use the actual server error serializer, including 401 expiry/revocation, 409 identity changes during reads/save/restore, feature-disabled 404, actionable validation/provider errors and failed Forget requests. They verify that another account cannot recover held text and that local clearing does not imply server revocation succeeded.

Two disposable local HTTPS/Chrome attempts were made with synthetic accounts, temporary SQLite, in-memory object storage and no publication. The HTTPS facade, production-cookie server and private-storage probe started, but browser page initialization was blocked: first Page.enable timed out; the diagnostic retry reported Chrome GPU process access denied (0xC0000022) and a fatal renderer startup failure. **Zero browser acceptance cases passed.** No sandbox or OS security workaround was attempted. Tracked browser/backend processes and the listener were stopped and temporary directories removed; additional descendant enumeration was OS-denied and was not retried. Exact evidence is in the task-root newsroom-https-browser-evidence.json and attempt logs. Optional manual browser harness sources are preserved separately from the primary release patch and remain unverified beyond syntax/startup.

The predecessor candidate passed trusted-HTTPS Linux browser acceptance, including cookie persistence, private/cleared contexts, expiry/revocation/logout, actual photo processing and repeated draft copies. The approved duration/renewal and old-draft-copy changes require fresh boundary tests and exact-release-head browser CI. A passing runner-local test does not establish the deployed TLS/proxy/storage configuration.

## Before any live activation

The approved scope is self-written own articles (including publication), verified admin/editor eligibility, a 30-day absolute maximum and 7-day inactivity deadline refreshed on each successful confirmation, twenty saves and publishes per hour each, six photo-ticket requests per hour, twelve distinct photo attempts per rolling day, and JPEG/PNG/WebP images up to 10 MiB. Older saved drafts may reopen as new copies; direct publication of the old draft remains subject to the existing freshness check. Deploy compatible code with the feature disabled, verify health/version, then explicitly enable `NEWSROOM_BROWSER_SESSIONS_ENABLED=true`. Each person must still sign in normally and opt in with their current password. Never infer authority to recover credentials or silently issue a remembered cookie.

The final task-root `NEWSROOM-SESSION-VERIFICATION.json` records exact checks, source/patch hashes, and remaining validation limits. Check the recorded aggregate outcome before release. CI on the eventual release revision and actual browser visual acceptance remain release checks; the earlier member aggregate result is not presented as validation of this standalone candidate.
